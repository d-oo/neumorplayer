`docs/design/`에 있는 디자인 zip(README.md + `*.dc.html` + 스크린샷으로 구성된
"design_handoff" 번들)을 이 리포지토리에 구현할 때 따르는 절차입니다. 시안마다
구체적인 요구사항(인터랙션을 얼마나 실제로 동작하게 할지, 데이터를 실 API로 붙일지
등)은 매번 다르므로 여기엔 넣지 않습니다 — 아래는 매번 반복해야 하는 "일하는 방식"만
정리한 것입니다.

## 1. 구현 전에 원본을 통째로 읽는다

압축을 풀고 README.md와 `.dc.html`을 **먼저 전부** 읽습니다. 스크린샷이나 README의
글로 된 설명만 보고 근사치로 스타일 값(px, 색상, 그림자)을 짜지 마세요 — `.dc.html`의
인라인 `style`이 실제 정답이고, 나중에 값이 달라 여러 파일을 다시 고치는 이중 작업을
막아줍니다. README의 "Fidelity"/"Design Tokens" 절이 픽셀 단위 재현을 요구하는지,
값을 단순화해도 되는지부터 확인하세요.

## 2. 기존 컴포넌트/토큰 재사용을 먼저 확인한다

- `docs/feature-conventions.md`의 feature 폴더 배치 기준(그 도메인을 대표하는
  feature가 있는지)을 따라 새 파일 위치를 정합니다.
- 시안의 마크업이 기존 컴포넌트(카드, 버튼, 썸네일, 검색창 등)와 비슷하면 새로
  만들지 말고 그대로 import하거나 최소한으로 확장합니다.
- 시안 값이 `src/index.css`의 기존 디자인 토큰과 정확히 일치하면 그 토큰을 그대로
  씁니다. 값이 미묘하게 다르면 섞지 말고, 그 값이 **여러 곳에서 재사용될 때만**
  새 토큰으로 등록하세요 — 한 곳에서만 쓰이면 로컬 상수/인라인 style로 둡니다.
  단, `:active`/`:hover` 같은 의사 클래스가 필요한 다중 그림자 값은 인라인
  style로 표현할 수 없으므로 한 곳에서만 쓰여도 토큰으로 등록해야 합니다(콤마가
  있는 `shadow-[...]` 임의값 클래스는 무시될 수 있음).

## 3. 제품/데이터 관련 결정은 추측하지 않고 물어본다

시안 자체에 답이 없는 것들 — 인터랙션을 얼마나 실제로 동작하게 만들지, 데이터가
실제 API인지 목업인지, 새 라우트를 어느 인증 가드 안에 둘지, 정책/제약(예: 외부
API 이용 정책)에 걸리는 부분이 있는지 — 은 짐작하지 말고 사용자에게 확인합니다.
플랫폼 정책처럼 리서치가 필요한 부분은 먼저 조사해서 근거와 함께 제안하세요.

## 4. 픽셀 단위로 정확히 재현한다

색상/그림자/타이포/간격은 시안 원문 값 그대로 옮깁니다. 표준 Tailwind 스케일과
정확히 일치하면 표준 유틸리티 클래스를 쓰고, 안 맞으면 임의값(`[...]`) 문법을
그대로 씁니다 — 어색해 보여도 반올림하지 마세요.

## 5. 구현 후 검증한다

`npm run build`/`npm run lint`를 실행하고, 가능하면
`.claude/skills/run-neumorplayer/SKILL.md`로 실제 화면을 스크린샷해 시안과
직접 비교합니다.
